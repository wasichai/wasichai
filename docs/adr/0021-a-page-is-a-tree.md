# ADR-021: A page is a tree

**Status**: accepted · 2026-09-19 · amends ADR-011

> Imported from sapgis on 2026-09-25. Identifiers renamed sapgis → chawpi; the decision is unchanged. See [sapgis origin](../sapgis-origin.md).

## Context

A record detail page's components were a flat list. Each one carried `column: Int` to say which
half of a two-column page held it, and `tab: String?` to say which tab it belonged to. Grouping
happened at render time: `pageTabs.ts` walked the flat list and built tab groups from equal strings,
in first-appearance order.

That model was deliberate and it bought what it was meant to buy. Tabs shipped without a migration,
without breaking a single stored row, and without touching the renderer's existing tests, because a
page where nobody typed a tab name rendered exactly as it did before.

It stops at the point where a tab is something you *place*. An admin who wants a section grouping
three fields above a map, inside the second of four tabs, cannot express it: there is no container,
and "section" is not a string that fits into the model. The editor was honest about this —
`PageBuilderPage.tsx` is a stack of per-component forms, and its own comment says so:

> `// form-based page editor. drag and drop is a later phase; this already covers the model.`

This is that later phase for the model. The canvas that edits it is a separate phase.

## Decision

**A page's components become a free tree.** Any container — `TABS`, `TAB`, `SECTION` — holds any
children, to any depth: a section inside a section, tabs inside a section inside another tab.

A bounded tree was the recommendation on the table — `Page → Tabs → Columns → [Component |
Section]`, the shape Salesforce's Lightning App Builder uses. It buys predictability: a validator, a
renderer and a canvas that only ever handle four fixed levels, never recursion. It was rejected in
favour of unlimited nesting, because a bound at four levels reintroduces the same wall the flat model
had already hit, one level further out — a tab strip inside a section inside a tab is exactly the
kind of thing an admin will eventually ask for, and a bounded shape cannot grow to allow it without
becoming a different, deeper bounded shape next time. Choosing the free tree means validation, the
renderer and the future canvas all become recursive; that cost is paid once, here, instead of being
paid again the next time the bound turns out to be one level short.

**A free tree still needs bounds, but they are guard rails, not design limits.** Depth is capped at
10: past that, a hand-written `definition` blows the validator's own recursive stack before Postgres
ever sees the request. Node count is capped at 200 — the lesson of `/api/gis/layers`, which once
crossed the 256 KB `DataBufferLimitException` because nobody had bounded a response; this one is
bounded before it is born. Neither number is reachable by dragging: they exist for a `definition`
typed or generated by hand, not for anything an editor can produce.

**`TABS` accepts only `TAB` children, and a `TAB` exists only inside a `TABS`.** This is not a
restriction on how free the tree may be — a `SECTION` may still hold a `TABS` that holds a `TAB` that
holds another `SECTION`, arbitrarily deep. It is a rule about what the types *mean*: a tab strip
whose children are not tabs has nothing to hang a label on, and a `TAB` with no strip around it has
nowhere to attach its label to. `SECTION`, which makes no such structural claim, accepts anything.

**`layout` sits on every container, not on the page.** Each container — the page root included, since
the root is a container too — declares its own `SINGLE_COLUMN` or `TWO_COLUMN`, and its children
carry `column` against *their parent's* layout, never the page's. The alternative was an explicit
`ROW`/`COLUMN` node pair, which turns every drop target into a literal `children` array — cleaner for
a future canvas — at the cost of two node types that draw nothing and exist purely as scaffolding.
It was rejected for what it does to layouts not yet asked for: a 2:1 split, or three columns, is not
a new *kind* of thing to place on a page, only a different way an existing container divides its own
children. Putting `layout` on `PageComponent` as an enum means that split is a new value of
`PageLayout` the day it is wanted, not a new node type the tree, the validator and the renderer all
have to learn to walk around.

**`V10__a_page_is_a_tree.sql` is one-way.** The alternative — keeping the renderer and the validator
able to read both the flat list and the tree — was rejected: it means two renderers and two
validators for as long as the product lives, to save a migration that runs exactly once.

The rewrite groups components sharing a `tab` into one `TABS` node holding one `TAB` per distinct
name, in first-appearance order, and strips the `tab` key from every component afterward.
Components with no `tab` move to the page root, ahead of the strip. **That is the one place the
migration changes what a page looks like.** Today, an untabbed component on an otherwise tabbed page
is caught by `pageTabs.ts` into a group named `''`, which the renderer draws as a tab of its own,
labelled `t('pages.tabs.page')`, positioned wherever the first untabbed component happened to appear.
After V10, those same components sit at the root, above the strip. A page where every component is
tabbed, or none is, migrates with no visible change at all; only a mixed page moves — to the reading
a tree can express and the flat list could not: content that belongs to the page rather than to any
one tab. Emitting a titleless `TAB` instead, to reproduce the old appearance byte-for-byte, was
considered and rejected: it would carry the flat model's workaround into the tree and force the
renderer to keep a permanent special case for a tab with no name.

## Consequences

- Validation, the renderer and the future canvas all walk children recursively instead of iterating a
  flat list; `pageTabs.ts` and its test, which built tab groups from equal strings, are deleted —
  a `TABS` node is now explicit, there is nothing left to group.
- "The first `FORM` owns saving" moves from a single `findIndex` over a flat array to pre-order
  depth-first traversal of the tree; the rule itself is unchanged, only how it is found.
- `column` is checked against the *parent's* layout, not the page's — the whole point of letting each
  container own its layout: `column: 2` inside a `TWO_COLUMN` section that itself sits inside a
  `SINGLE_COLUMN` page is valid and must stay valid.
- `WorkflowStates`, the port `pages` and `data` already share, gains `transitionNames` so an `ACTION`
  can be validated against the object's real transitions — pages validate against them, the record
  path never needs to ask.
- Stored pages migrate once, through V10. Generated pages need no migration at all: `generate()`
  simply emits the new tree shape on every request, since nothing about them is ever stored.
- The bounded tree that was recommended and turned down remains available as a later, stricter
  option if the free tree ever proves too permissive in practice; nothing here forecloses it, but
  nothing here builds toward it either.
